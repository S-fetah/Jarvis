01 · The Idea

One assistant that does real work — safely

Not a chat toy: an agent that plans, acts with permission, and proves the result.

The experience

  • Ask in plain language for multi-step, practical work: research, coding, summaries, PDFs, downloads, dev servers.
  • Jarvis shows its plan and live progress, asks before anything sensitive, and verifies outcomes — a file exists, a server listens, a command exits clean.
  • Report comes back with links to everything it produced.

Why local-first

  • Files, credentials, and tool execution stay on your machine.
  • The model gateway runs locally; providers are called through it — never hardcoded, never locked in.
  • Autonomy is a spectrum under your control: every side effect is classified, logged, and gated where it matters.
"Reason about a task, show progress, use approved tools, verify the outcome, report clearly."

First-release scope — and hard non-goals

Balanced coverage across browsers, code, and documents; never unrestricted control.

Deliverables

  • Chat UI with streaming, task progress, approvals, and history
  • Browser search + structured automation (Playwright-class, not mouse simulation)
  • Approved-folder file read/write + summarisation
  • PDF creation with output verification
  • Project tooling: tests, dev servers, process inspection + approved stops
  • Image generation via a supported provider

Non-goals / guardrails

  • No cloud-hosted agent — sensitive actions stay local
  • No unrestricted shell or computer control
  • No extracting or pooling subscription quotas (Codex plans are not API quota)
  • Web content is untrusted input, never authority over the user's request
  • General desktop UI automation deferred — too fragile for v1
JARVIS · ARCHITECTURE03 / 16
03 · Approach

Evidence-driven, policy-first, incremental

Every layer of the design was validated by a spike before it was committed to.

Prove, then expand

One model, one well-bounded tool, one verified loop first. Toolset and model routing grow in small, verifiable steps — never all at once.

Policy before features

The permission engine and approval binding were designed and unit-tested before the agent loop that needs them (ADR-004).

Benchmark, don't assume

T-001 validated the gateway's real latency and failure modes; T-002 benchmarked an existing agent to decide build-vs-embed with evidence.

Build custom, embed nothing

T-002 showed Open Interpreter was not embeddable and its default gates too weak — so Jarvis runs a thin purpose-built orchestrator in its trusted process (ADR-002).

Replaceable gateway

All model traffic flows through one IModelGateway adapter. FreeLLMAPI is the first backend; Ollama, LM Studio, or direct APIs can replace it without touching agent logic (ADR-003).

06 · Security Model

Audited, remediated, regression-tested

2026-10-23 audit found 11 issues (SEC-001…011) — all P0/P1 findings remediated with 22 automated tests.

Hardened boundaries

  • Command injection eliminated — parameterized spawn(shell:false), strict URL protocol checks (SEC-001)
  • HMAC approval verification wired into the runtime resolver, anti-tamper tested (SEC-002)
  • Credentials encrypted via Electron safeStorage (DPAPI) in SQLite; renderer only sees a hasApiKey flag (SEC-003)

Window & filesystem defense

  • Sandbox + context isolation enforced; navigation guards and window-open handler (SEC-004/005/011)
  • Symlink traversal blocked — realpath resolution on every tool path (SEC-006)
  • Extension gating — .bat .cmd .ps1 .exe treated as high-risk (SEC-007)
  • Atomic persistence — no torn writes on crash (SEC-010)

07 · Permission Model · ADR-004

Six categories, cryptographically bound approvals

Stricter than the benchmarked competitor default: outside reads are gated too, not just writes.

CategoryScopeDefaultUI
read_inFiles inside an approved workspaceAllowedLive timeline
read_outAnything outside workspaces (Desktop, profile)ApprovalModal + full path
write_inCreate/modify inside workspaceNew files OKTimeline + diff
write_outCreate/modify outside workspacesApprovalModal + content preview
processChild processes, dev servers, scriptsApprovalModal: exe + args + cwd
networkSearch, navigation, downloadsRead-only OKTimeline + URLs + bytes

Approval binding

Every approval = HMAC-SHA256(action ∥ workspace ∥ args-hash, session-secret). Single-use, expires in 5 minutes. Change one argument — the token fails.

Denial semantics

Deny permanently invalidates the token. The runtime never silently retries a denied action — it halts the branch and asks for new guidance.

JARVIS · ARCHITECTURE08 / 16
08 · Gateway Boundary · ADR-003

One adapter, deterministic models, honest failures

Designed directly from measured gateway behavior (T-001), not vendor claims.

Deterministic routing

  • Profiles pin concrete model IDs (fast / reasoning / coding / vision) fetched live from GET /v1/models
  • Gateway "auto" routing measured non-deterministic — reserved as fallback only

Failure semantics

  • Local gateway down (ECONNREFUSED) vs upstream error (502/503/504) are distinct signals
  • Transient 5xx → exactly one retry after 3 s, exponential backoff
  • Never auto-retries side effects; inference requests only

Latency instrumentation

TTFT clock starts at fetch() dispatch — capturing connect + queue (measured gap: ~3.3 s hidden in connection). Telemetry logs pinned model, routed model, TTFT, total, tokens.

Credential boundary

Keys live only in env vars or DPAPI-encrypted storage — never in SQLite plaintext, never in Git, never in the renderer, never in event streams shown to the model.

10 · Operating Modes · ADR-001

Three modes — latency without recklessness

Racing is a hedge against slow routes; it never applies to side effects.

Normal

One pinned model per profile. The default for everything. Predictable routing, clean telemetry, lowest cost.

Racing

For eligible read-only requests only: fire a bounded race across profiles, take the first valid response, cancel the losers. Never for tools, downloads, mutations, or sensitive prompts.

Multi-agent

Separate visible model roles (researcher, coder, reviewer) — each policy-bound. Not unrestricted parallel tool control; one shared approval timeline.

Why this exists

Measured spread on the same gateway: 1.4 s to 64 s for equivalent work. Hedging read-only turns with a cancel-losers race turns worst-case waits into typical-case ones — without ever racing an action that touches the system.

11 · How It Works

Request lifecycle — one turn, end to end

Every turn walks the same policy-checked path; the user sees each step live.

Prompt arrives in the renderer; the typed bridge forwards it to main.
Plan — the orchestrator drafts steps and required tool categories.
Policy classify — each intended action is mapped to read/write/process/network tiers.
Gateway call — pinned model, streaming deltas; TTFT + total recorded.
Approval gate — gated actions raise an HMAC-bound modal; deny halts the branch.
Execute sanitized — -NoProfile, minimal env, parameterized spawn, scoped paths.
Verify outcome — file exists, server listens, exit code checks. Claims are not enough.
Feed results back — verified outputs return to the model for the next step.
Timeline + history — every event lands in the activity timeline and SQLite audit store.
Report — summary with links to produced artifacts; failures surface honestly.

JARVIS · ARCHITECTURE14 / 16
14 · How It Will Work

The target experience

What "done" looks like when the phases land.

"Research this and make me a PDF"

Jarvis searches the web with structured automation, cross-checks sources, drafts the document, generates the PDF through an approved write, opens it to verify it renders, and hands you the link — with every step visible in the timeline.

"Get this project running"

It inspects the codebase, runs the test suite, and starts the dev server — each process launch approved once and tracked. It reports the listening port and only ever stops processes it started, after asking.

Always-on, low-friction

Tray-resident with the mascot and quick-chat drawer; the main window for real work. Model profiles switch per task; Racing mode keeps read-only answers fast; rate limits recover gracefully with your guidance.

Trustworthy by construction

Every outside-scope action stops at a modal bound to the exact arguments. Denials are final. The full audit trail — plans, commands, outputs, approvals — lives locally in SQLite, exportable and inspectable.
