What it does

  • Chat → model picks tools → Jarvis executes → model writes the answer.
  • Files, PDFs, web search, downloads, dev servers, Chrome control, email, screen capture, memory.
  • Shows a live timeline; risky steps should wait for approval.

Where it runs

  • One Windows PC, one Electron app, four windows + tray icon.
  • Models: cloud APIs (13 keyed/keyless) or local Ollama.
  • State on disk: SQLite (sql.js), DPAPI key vault, USER.md memory.

Not there yet

  • Approval covers 1 of 6 risky actions (slide 18).
  • No task cancellation; agent loop capped at 5 turns.
  • Replies arrive whole, not streamed, in the agent path.

System prompt assembly

PromptEngine.buildSystemPrompt() composes one system message per model call from fixed and user-controlled layers.

1 · Identity & safety anchors
Who Jarvis is; immutable rules that later layers cannot override.
2 · Privacy statement
Data stays local; no technical leakage in replies.
3 · Tool usage guide
Per-tool rules: Chrome profile must be asked, Gmail flow, shortcuts, intent classification (question vs task).
4 · Style · mode · depth
direct | balanced | detailedchat | debug | build | planquick | standard | deep
5 · USER.md memory
Profile, dev defaults, standing notes — injected every call.
6 · Custom prompt
User text from Settings, scanned by scanPromptSafety(); risky text needs an explicit acknowledgement.

Plus, per run

  • Skill Advisor system hint when a skill matches the goal.
  • Action Verification user message when the model falsely refuses on turn 1.
  • Synthesis nudge at turn 4 of 5.

Prompt-safety scanner

src/shared/prompt-safety.ts flags bypass phrases, jailbreak patterns, destructive commands (rmdir /s, format c:, drop database) and credential exfiltration in the user's own custom prompt.

Gap

Text coming back from tools (web pages, files) is not scanned or labelled as untrusted before the model reads it (acceptance F).

III · Intelligence

Failover & cooldown

Inside one chatWithTools call — tools are never re-run by a failover, only the model request is retried elsewhere.

1 · Build queuegetFailoverQueue(primary) — primary first, then ready providers
→
2 · Try entry iprovider.chatWithTools(…)
→
3 · 429 / rate_limit?recordCooldown(provider, 75 s), move to i+1
→
4 · Successreturns activeModel, isLowQuota

What the user sees

  • Timeline: "Seamless Failover → model" when the active model differs.
  • Reply footer: "Low Token Quota Alert" when isLowQuota.
  • All providers exhausted → RateLimitCard with a retry timer.

How "low quota" is decided

isLowQuota = i ≥ queue.length − 2 — a position heuristic (running on one of the last two fallbacks). The "~10k tokens left" text is not measured.

Second safety net

If the balancer throws, the adapter retries through the legacy FreeLLMAPI endpoint with its own bounded retry and thinking-block extraction.

ADR-003 rule kept: a model is pinned per profile; auto routing and failover are resilience, and every switch is shown — Jarvis never changes provider silently.

IV · Safety

Permission model — ADR-004

Six categories decide whether an action runs, asks, or is refused. Approvals are bound to the exact arguments.

CategoryDefinitionDefault
read_inRead inside the selected workspaceAllowed
read_outRead outside the workspaceApproval (today: denied)
write_inCreate/modify inside workspaceNew: allowed · overwrite/delete: approval
write_outWrite outside workspaceApproval
processSpawn processes, dev servers, scriptsApproval
networkSearch, navigation, downloadsAllowed (downloads to staging)

Approval token

hash = HMAC-SHA256(sortedJSON(args), sessionSecret)

  • 32-byte secret, new every launch.
  • Expires after 5 minutes; single use.
  • Any argument change → hash mismatch → refused.
  • Deny evicts the request; no silent retry.

Also enforced

Real-path resolution against symlink/junction escape (SEC-006); executable and hidden-file creation needs approval (SEC-007); child processes spawn with shell: false (SEC-001).

Spec vs code

ADR-004 binds action type + workspace + args. Code hashes args only.

Approval flow

From a gated tool call to execution. The approved action runs outside the agent loop.

1 · ToolExecutore.g. start_dev_server
→
2 · evaluateAction()category → requiresApproval · request stored in pending map
→
3 · onRequestApprovalindex.ts builds a TaskState waiting_for_approval
→
4 · RendererApprovalDialog: exact command, cwd, impact; mascot shows "needs approval"
▼
8 · Reporttimeline event + chat message "Action Approved & Executed"
←
7 · executeApprovedAction()browser launch · dev server · shell command
←
6 · verifyApprovedAction()hash match · not expired · consume token
←
5 · approval:resolvesender check · granted / denied

Meanwhile, the model…

gets "gated — tell the user you are waiting" as the tool result and the run ends. It never learns whether the action ran or what it produced.

Denied

Request evicted, task marked cancelled, chat records "Action Cancelled". The model cannot retry the same token.

Fail-open edge

If no approval handler is wired, start_dev_server skips the gate and runs (acceptance C).

Four stores, all local. Only provider keys are encrypted at rest.

Provider vault

userData/provider_vault.json

API keys encrypted with DPAPI (safeStorage), bound to the Windows user. Also holds hub state: enabled providers, local-server flag/port.

USER.md

<workspace>/USER.md

Plain Markdown: profile, dev defaults, standing rules. Injected into every system prompt; edited by manage_user_memory, the Settings app, and accepted LearningEngine suggestions.

Artifacts

output/ · output/diagnostics/

PDFs, downloads, screenshots, sanitized diagnostics bundles (Markdown + JSON, secrets redacted).

Agent memory, honestly

Long-term memory = one Markdown file. No embeddings, no search over past runs, no record of which strategies worked.

Path risk

dbPath = process.cwd()/userData. A packaged app started from autostart or another folder gets a different, empty database.

Privacy

USER.md is tracked in git and holds personal contact data. Chats and memory are not encrypted at rest.

Browser automation — three channels

Zero-dependency Chrome DevTools Protocol driver (utils/cdp.ts, 489 lines) plus launch and keystroke fallbacks.

1 · Launch

launchBrowser() runs chrome.exe with a chosen --profile-directory, optionally minimized/off-screen. Profiles discovered from Chrome's Local State. Rule: always ask which profile.

2 · CDP (deterministic)

Needs Chrome started with --remote-debugging-port=9222.

GET /json/list/json/new/json/closeWebSocket Runtime.evaluate

Read page text, click by selector/text, scroll, close tabs, wait for Gmail compose DOM then click Send.

3 · Keystrokes (blind)

PowerShell WScript.Shell.SendKeys into the focused window: Ctrl+Enter, Ctrl+W, Ctrl+Shift+T. Used when CDP is not available. No verification of what received the keys.

Not there yet

V · Subsystems

Processes & dev servers

ProcessManager (246 lines) owns every child process Jarvis starts — and only those.

Spawn — child_process.spawn, shell: false, hidden window, working dir = selected project. No admin rights.
Register — Map<id, {proc, state}> with command, PID, cwd, status starting | running | stopped | failed.
Observe — rolling recentLogs buffer from stdout/stderr; port detection by log parsing + polling.
Broadcast — onUpdate → process:updated → ProcessStrip in the UI and preview in the Workspace Canvas.
Stop — by Jarvis id only: taskkill /pid N /t /f kills the whole tree. stopAll() on app exit.

Verified

  • Unknown ids and foreign PIDs are refused (acceptance C).
  • Dev-server start asks first with exact command + cwd.

Workspace Canvas

Split pane showing the running server (iframe), local PDFs (blob URL in <object>), web pages and code, with desktop/mobile emulation.

Missing

No general "run this command" tool, no test runner tool, no long-running job queue. Process state is lost on restart.
